# Install (Docker Compose)

This is the only supported install path today. There are no published images, Helm chart or
release artifacts; the images are built from your checkout. **Verified (2026-11-03):** the local development profile (`make dev`) builds and its four services
(migrations, api, worker, dashboard) run healthy, and sign-up, dashboard pages, demo sign-in and a
Verdict v2 analysis page work in Chrome. **Unverified:** the production-like procedure below, a
clean-machine run, and anything against real GitHub. The production steps come from `Makefile`,
`docker-compose.yml`, the Dockerfiles and the code.

## Prerequisites

| Need | Detail |
|---|---|
| Docker with Compose v2 | `docker compose config -q` parsed the shipped `docker-compose.yml` with Compose 5.3.1. Older v2 releases: unverified |
| git | To clone the repository |
| Free host ports | `3000` (dashboard), `8000` (API), `5432` (PostgreSQL; change with `POSTGRES_HOST_PORT`) |
| Time | The first build takes several minutes (README cites about 10 on a cold cache); later starts are faster |
| Optional: GNU make | `make dev`. On Windows without make use `.\scripts\dev.ps1 dev` |
| Optional: a GitHub App | Needed to analyse real pull requests, see [DEPLOYMENT.md](../DEPLOYMENT.md) section 4 |

Disk, RAM and CPU sizing: **Unverified**, nothing in the repository measures it. The bundled PostgreSQL is
`postgres:16-alpine` with data in the named volume `radius-postgres-data`.

## Two ways to run it

| | Local development (`make dev`) | Production-like (`docker compose up`) |
|---|---|---|
| Files | `docker-compose.yml` + `docker-compose.dev.yml` | `docker-compose.yml` only |
| `RADIUS_ENV` (api) | `development` | `production` |
| `.env` | generated by `make env` with random secrets | you write it from `.env.example` |
| API key | one random dev key (`RADIUS_API_KEY`), registered as `API_KEYS=<org>:<key>` for the dev organization | you set `API_KEYS` (or managed keys) |
| CORS | `http://localhost:3000` and `http://127.0.0.1:3000` | exact `https://` origins in `CORS_ORIGINS`, nothing automatic |
| Sign-up | auto-verified (`DEV_AUTO_VERIFY_EMAIL=true`); links are also printed in the api log (`EMAIL_DELIVERY_MODE=log`) | verification mail over `SMTP_*`; not auto-verified |
| Missing secrets | `make dev` stops with "Run `make env`" | Compose stops: `SESSION_SECRET is required` |

The dev profile is for a laptop only. Do not expose it to a network.

## Steps: local development

```bash
git clone https://github.com/Mohith-c7/Radius.git && cd Radius
make dev          # or: .\scripts\dev.ps1 dev
```

`make dev` runs `python scripts/gen_dev_env.py` (creates `.env` from `.env.example` with a random
`SESSION_SECRET` and a random `RADIUS_API_KEY`; it never overwrites an existing `.env`), then
`docker compose --env-file .env -f docker-compose.yml -f docker-compose.dev.yml up --build -d --wait --wait-timeout 300 postgres migrations api worker dashboard`.
Compose starts PostgreSQL, runs the one-shot `migrations` service (`alembic upgrade head`), then the
API, worker and dashboard once their dependencies are healthy.

If you already have a `.env` from an older version of this repository, delete it (or copy the
new variables from `.env.example`) and run `make env` again; the old file has the public placeholder
session secret and no dev API key, and `make dev` will say which value is missing.

Check it:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml ps    # api, worker, dashboard, postgres
curl -f http://localhost:8000/api/v1/health
curl -f http://localhost:8000/api/v1/ready      # 503 if the database is unreachable
```

Open the dashboard at http://localhost:3000 and the API docs at http://localhost:8000/docs.
Sign up with any e-mail address: the account is verified immediately, and the verification link is
also printed in `make logs` (look for `[Radius Email (EMAIL_DELIVERY_MODE=log)]`).

How the dashboard reaches the API in this profile: the browser calls `/api/radius/*` on the
dashboard, whose server-side proxy adds `X-Radius-API-Key` (`RADIUS_API_KEY`) and
`X-Radius-Organization-Id` (the dev organization `00000000-0000-4000-8000-000000000001`). Sign-in
calls go from the browser straight to the API at `http://localhost:8000/api/v1/auth/*`, which is why the
dev profile allows the `http://localhost:3000` origin. The organization id is also baked into the
dashboard bundle at build time (build argument `NEXT_PUBLIC_RADIUS_ORGANIZATION_ID`); after changing it
in `.env` rebuild with `make dev`. For illustrative data in that organization run `make seed-demo`
(opt-in, demo only).

**Verified (2026-11-03):** a full-stack run of this profile (build, services healthy, sign-up in a
browser, dashboard pages, demo data) was done in Chrome. The demo data was loaded by running
`scripts/seed_demo.py --yes` directly, which is the command `make seed-demo` wraps; the make target
itself was not run. Not covered: other browsers, other host operating systems than the one used, and
timing or sizing figures.
`scripts/check_compose.py` additionally checks the Compose files statically.

## Steps: production-like Compose

```bash
cp .env.example .env     # then edit; do NOT use the placeholders
docker compose --env-file .env up --build -d
```

Compose refuses to start until `SESSION_SECRET` is set. See the next section for everything else
you must set.

## First-run settings you must understand (production-like)

The Compose `api` and `worker` services run with `RADIUS_ENV=production` regardless of your `.env`
(`docker-compose.yml`). In production mode the API fails closed:

- `RADIUS_ALLOW_INSECURE_DEV` is honoured only in `development`/`test` and is not forwarded by
  Compose, so the keyless dev shortcut does not apply to the Compose stack.
- **API keys.** Protected routes answer 403 `ACCESS_DENIED` ("Radius API keys are not configured")
  until `API_KEYS` holds at least one `org_id:key` pair (`apps/api/src/radius_api/auth.py`). Set, in `.env`:

  ```
  API_KEYS=<org uuid>:<long random key>
  RADIUS_API_KEY=<the same key>
  NEXT_PUBLIC_RADIUS_ORGANIZATION_ID=<org uuid>
  GITHUB_DEFAULT_ORGANIZATION_ID=<org uuid>
  ```

  `RADIUS_API_KEY` is the server-side secret the dashboard proxy sends; it is never given a
  `NEXT_PUBLIC_` prefix. The org id must match between `API_KEYS` and the dashboard variable.
  Managed keys are preferred over `API_KEYS` ([API_KEYS.md](../security/API_KEYS.md)).
  **Unverified:** that the dashboard works end to end with these values on a fresh database.
- **CORS and sign-in.** `CORS_ORIGINS` must list the exact `https://` origin of the dashboard; production
  validation rejects `*` and `http://` origins and adds no localhost origin. Without it the browser blocks
  the dashboard's sign-in calls to the API. Serve both behind TLS (and set `SESSION_COOKIE_SECURE=true`,
  `RADIUS_HSTS_ENABLED=true`, `FRONTEND_ORIGIN`, `NEXT_PUBLIC_API_URL` / `NEXT_PUBLIC_RADIUS_API_BASE_URL` to the public URLs).
- **Webhooks.** `GITHUB_WEBHOOK_SECRET` is mandatory; unsigned deliveries get 403.
- **Dashboard sign-in.** Accounts are not auto-verified in production; configure `SMTP_*` so
  verification mail can be sent. `EMAIL_DELIVERY_MODE=log` and the published placeholder
  `SESSION_SECRET` values are refused when `RADIUS_ENV=production` (the API fails at start-up).
  Never set `DEV_AUTO_VERIFY_EMAIL` on a shared deployment.
- **Session secret.** `SESSION_SECRET` (32+ random characters) is required; there is no default in
  `docker-compose.yml`.
- **Database.** The bundled PostgreSQL uses the fixed credential `radius/radius` (container network
  only) and is published on `127.0.0.1` only. Use an external database with your own credential for real use.
- **Demo data.** `RADIUS_SEED_DEMO_DATA` is ignored in production mode. Use `make seed-demo` against a
  disposable database if you want illustrative data.

Compose forwards only the variables listed in `docker-compose.yml`. Anything else in
[CONFIGURATION.md](CONFIGURATION.md) needs a line in the service `environment:` block.

## Connect GitHub

Create a GitHub App, set `GITHUB_APP_ID`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_WEBHOOK_SECRET` (and
`GITHUB_INSTALLATION_ID` or `GITHUB_SINGLE_TENANT=true` plus `GITHUB_DEFAULT_ORGANIZATION_ID` for a single
organization), expose the API over HTTPS and point the App webhook at
`https://<api host>/api/v1/webhooks/github`. Permissions and events are in
[DEPLOYMENT.md](../DEPLOYMENT.md) section 4 and the validation checklist is
[github-app-validation/RUNBOOK.md](../github-app-validation/RUNBOOK.md). Note that linked-issue intent
ingestion additionally needs the `issues: read` permission (RUNBOOK section 0).

## What the first verdict looks like

Test execution inside the worker is off by default (`WORKER_TEST_EXECUTION_MODE=disabled`), so a first
pull request normally ends `insufficient_evidence` with the gap "Selected tests were not executed; upload
CI results to verify" (`packages/confidence/.../scoring.py`). To reach `verified`, run the selected tests in
your CI and upload JUnit XML or JSON bound to the head SHA ([CI integration](../CI_INTEGRATION_GUIDE.md)).
The check run is not re-published after a later upload (README, maturity table).

## Optional profiles

| Profile | Command | Purpose |
|---|---|---|
| `sandbox` | `docker compose --profile sandbox up sandbox-image` | Builds the test image only. The Compose worker has no container runtime, so sandbox execution is not available inside Compose ([security/CONTAINERS.md](../security/CONTAINERS.md)) |
| `observability` | `docker compose --profile observability up -d jaeger prometheus` | Jaeger (UI on 16686, OTLP on 4318) and Prometheus (9090). Also set `RADIUS_TRACING_ENABLED` / `RADIUS_METRICS_ENABLED`, see [OBSERVABILITY.md](../OBSERVABILITY.md) |

## Stop and reset

```bash
make down                     # keeps the database volume
docker compose down -v        # also deletes radius-postgres-data and radius-repository-cache (all data)
```
