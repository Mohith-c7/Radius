# Verdict v2 replay on this repository's merged PRs (2026-11-03)

**Status: exploratory, descriptive, NOT a pre-registered evaluation and NOT a research result.** This is the "first look at real data" that `docs/research/ALIGNMENT_LOG.md` (entry 2026-11-03) asked for, because all earlier evidence was 8 hand-written fixtures. It is outside the pre-registered RQs (`docs/research/preregistration/PREREGISTRATION.md`: exploratory runs carry no inferential claim); nothing here may be quoted as a measured accuracy, recall or false-positive rate. Treat every number as "what the code printed on 29 PRs", not as an estimate of anything.

- Tool: `scripts/verdict_v2_replay.py` (reproducible; cached per PR; read-only GitHub access, nothing posted). Raw per-PR results: `REPLAY_2026-11.results.json` (this directory).
- Code state: `develop` at `5db8f2e` plus the two fixes described in section 6 (`13e5ee0`, `f5e35ab`). The deterministic run (section 3) was started before the T015 fix, so PR #103 shows the pre-fix result there; the sensitivity run was started after it.

## 1. Method and honest limits

**What was run, per PR.** For each selected merged PR of `Mohith-c7/Radius`: metadata through `gh api -X GET` (title, body, author, refs, changed-file list); base and head commits resolved from git (merge commit: second parent and the merge-base of the parents; squash: parent and the commit itself); the head tree's `.py` files extracted with `git archive` into a temp dir (removed afterwards, 60 MB cap), base-side reads through git objects; the PR diff from `git diff base head`. Then, in-process and with no LLM and no network: the production source sanitiser, the deterministic criterion extractor (`DeterministicCriterionExtractor`) and rule-based testability rater on the PR title and body; Stage A (`VerdictStageACollector`: symbol changes, tamper rules, criterion to symbol links, symbol to test links, assertions, VS-04 relevance, repo policy at base); Stage B and the verdict rules. Closing-keyword issue links were parsed (`parse_closing_references`); none of the 29 PRs had any (so no issue text was available as intent). Each PR runs in its own child process with a 400 s hard timeout; PRs run sequentially.

**Selection.** Stratified: the 6 most recent eligible PRs of each of feat, fix, docs, ci (`ci`, `build`, `chore`, `security` prefixes) and "other" (non-conventional titles, `test`, ...), 29 PRs in total (only 5 "other" were eligible at the time of the run). Skipped before running: bots (dependabot), "Merge"/"Release" titles, branch promotions (develop to dev to main), PRs over 300 files (none hit). Eligible population: 81 merged PRs.

**Limits that matter for reading the numbers.**

1. **One repository, same team, same author.** 28 of 29 PRs are by the project owner, written with an AI assistant (the commit trailers say so; the agent-signal heuristic fired on 28 of 29, which downgrades test independence for those PRs). The repository is also the system under test (many PRs change the very pipeline replayed). Nothing generalises.
2. **Static evidence only; no CI per-case results exist for historical PRs.** Without results the shipped rules always stop at R2p ("awaiting CI results"), so every PR would read `insufficient_evidence`. To see anything else the script scores a **counterfactual**: every linked or changed test is **assumed to have passed** (no test was run). All verdicts and criterion states below are therefore a ceiling on static support under "CI green", never a statement that tests passed. The as-shipped verdict (R2p for all 29) is recorded per PR in the JSON.
3. **Intent from PR bodies that were not written for Radius.** The production deterministic extractor reads acceptance-style sections, checklists, Gherkin and spec files. It extracted **0 criteria from all 29 PRs** (section 3, finding F1). To see the downstream behaviour at all, a clearly labelled **sensitivity mode** (`--intent-mode bullets`) treats the PR title without its conventional-commit prefix plus top-level body bullets of at least five words as *proposed* criteria. That mode is a crude recall upper bound with unknown precision. It is an invention of this script (`replay-bullets-v0`), not product behaviour.
4. **Criteria stay `proposed`** (nobody confirmed them), which is what the product would see before a human confirms; the `unconfirmed` flag is set.
5. **No ground truth.** Whether a PR "deserved" `verified` is my reading of its diff and text, nothing more. Case-study assessments are one reviewer's judgement and not labels.
6. **Non-determinism under load.** Results depend on wall-clock budgets (F4); the same PR gave different tamper findings on two runs. Treat single-PR outcomes as unstable.
7. **Selection and survivorship.** Only merged PRs; early history (#3, #9: a dashboard import) is atypical; later PRs are mostly the Verdict v2 work.
8. **Data hygiene.** Only this repository's own public PR text was used and is quoted briefly. Features use information available at PR time (title, body, diff, commit messages); the merge commit is used only to locate the commits. No third-party data, no secrets, no PII (author logins are not reproduced). The raw cache stays in git-ignored `.cache/`.

## 3. Headline findings (read these first)

**F1. Extraction recall on real PR text is zero (29 of 29 PRs, 0 criteria).** `DeterministicCriterionExtractor` only turns lists under headings such as "Acceptance criteria", "Requirements", "Expected behaviour", "Definition of done", task-list checklists and Gherkin into criteria (`packages/intent/src/radius_intent/infrastructure/extraction/config.py:13-18`). Ordinary PR bodies ("## Summary" with bullets, "## Test plan") are ignored by design, and a heading like "## Acceptance (VS-02) - ..." does not full-match the section pattern, so even PR #100's acceptance paragraph is lost. The consequence is not a small recall problem: with the product as shipped and no `.radius/intent.yml`, **the intent layer contributes nothing on this team's own PRs**, and Verdict v2 degenerates to "tamper rules plus symbol-level rules R2a/R4".

**F2. A PR with no criteria can be `verified` (rule R4).** 11 of 29 PRs are `verified` with 0 criteria (docs, CI, licence, dependency bumps, a test-only change). R2a only fires when the PR changes behavioural Python symbols; everything else passes vacuously with intent coverage 1.00. A maintainer reading "verified" on a LICENSE or workflow change would say the word means nothing there, and on a security-relevant CI change (e.g. #86 dropping a cache, #80 bumping action versions) it is positively misleading. Even in sensitivity mode, docs PRs #94, #95, #104 and test-only #106 are `verified` because their single criterion (the title) is rated "subjective or vague", is *excluded*, so unproven mass is 0.

**F3. Tamper rules decide every `failed` verdict, and at least three of seven decisions look wrong.** All 7 `failed` (R1c) verdicts come from a single high-severity tamper finding and nothing else. My reading of each (not ground truth):
- #40 (T001 `test_deleted`): the "deleted" test was **renamed** (`test_trace_context_round_trips_through_carrier_store` to `..._through_traceparent`) with a modified body; move detection only matches identical text (`packages/analysis/src/radius_analysis/tamper/rules/disabling.py`, `_head_test_texts` and the `p.base.text in moved_keys` check). False positive.
- #91 and #101 (T002 `runtime_skip`, high): `pytest.skip('prometheus_client not installed')` and `pytest.skip('no previous docs/api/openapi.json reachable in git')` are environment guards inside brand-new tests. The rule flags any `pytest.skip(...)` added to a test body at high severity and confidence 0.8, with no distinction between a conditional guard and an unconditional skip, or between a new test and a skip added to an existing one (`disabling.py:120-130, 204-212`). False or at best overstated.
- #103 (T015 `hardcoded_secret`, high): `GEMINI_API_KEY_ENV = "GEMINI_API_KEY"` (the *name* of an environment variable). Clear false positive; **fixed** (section 6).
- #87 (T010 `continue_on_error`, high) in a container-scan workflow and #22 (T017 `collection_hook`, high: `collect_ignore` in a benchmark-fixture `conftest.py`): defensible to surface for a human, but both read as advisory scan / fixture-isolation settings; I would call `needs_review`, not `failed`. #109 (T004 `conjunct_dropped`, high): an assertion was shortened when a title string changed; plausible true positive but I did not verify it.
A maintainer who saw `failed` on #40, #91, #101 and #103 would stop trusting the signal quickly. `failed` is also the verdict word that reads as "do not merge".

**F4. Results depend on machine speed (non-determinism by time budget).** The tamper context has a wall-clock budget (`context_time_budget_exceeded`, which yields a `truncated` report) and Stage A has 60 s per step and 120 s overall (`CollectLimits` in `collect.py`). On PR #100 one run produced 82 tamper findings and another, under more load, 0 findings with a `truncated` marker (the verdict changed between `failed` and `insufficient_evidence`). In the second sensitivity pass four producers on #100 and one on #107 hit `producer_timeout`. A verdict that changes with CPU contention is not auditable. (Part of the cause was F5, now fixed.)

**F5. Tamper analysis timed out on 5 of the first 29 runs (17%), a Windows-specific performance defect, now fixed.** `GitSnapshot.read` ran one `git show` process per probe, and the dependency rule probes dozens of manifest and `__init__.py` paths that do not exist (537 spawns, 82 of 85 seconds on PR #107 at ~0.15 s each). Critical-producer timeout means `StageAError` and v1 stays published. After the fix the same analysis takes 15.6 s. Linux spawn cost is lower, so production would see this less, but the cost of "probe for absent paths by spawning git" scales with PR size everywhere.

**F6. Non-Python work is invisible.** `unsupported_language:typescript/javascript` appears on 4 PRs; #3 (20 TS/JS files) has 37 changed symbols, 31 unlinked, no tests linked, and reads `insufficient_evidence` by R2a. #82 (Next.js and advisories patch) is `verified` with zero criteria because it changes dependency manifests only. YAML, Dockerfiles, workflow files, Markdown and lockfiles produce no behavioural symbols, so by design nothing can be proven or refuted for them (and R4 then calls them verified, F2).

## 4. Twelve case studies

Notation: "det" is the product as shipped (deterministic extractor), "bullets" is the sensitivity mode, both in the all-green counterfactual view. Criterion states: unevidenced / weak / excluded. Links are to the PRs on GitHub (public).

**1. Well-specified feature: [#102](https://github.com/Mohith-c7/Radius/pull/102) feat(api): managed API keys with scopes, rotation, revocation (20 files, 10 Python source, 2 test files).**
det: 0 criteria, `insufficient_evidence` by R2a (nothing extractable; two tamper findings: `# pragma: no cover` medium, a stub low). bullets: 4 criteria. One is the title (excluded as vague), "Scopes enforced centrally via a path/method mapping..." is unevidenced (structural), "Storage: HMAC-SHA256 fingerprint with a server-side pepper" is **weak** (S 0.47, the only criterion in this PR with partial support), "Tests: lifecycle, scopes, legacy keys, audit, cross-org isolation... 100% coverage" is unevidenced and typed non-functional ("needs typed evidence"). Verdict `insufficient_evidence` by R2b, coverage 0.60.
Assessment: the best-case PR for the system (feature, tests present, clear prose) and the output is still not what a maintainer wants. The criteria are sentences from a *summary* written after the fact, not requirements; two of the four are descriptions of the implementation ("Storage: HMAC-SHA256..."), one is a test inventory. "weak" for the storage bullet is plausible (tests exist), but nothing tells the reviewer *which* tests or what they assert beyond a score. Useful part: the PR was not called verified and the rule trace is readable. Misleading part: the list looks like an intent checklist but is really the PR description, so "4 criteria, 1 weak" invites a false reading of coverage.

**2. Docs-only: [#104](https://github.com/Mohith-c7/Radius/pull/104) docs(research): second independent alignment review (1 file).**
det and bullets: `verified` by R4, intent coverage 1.00, UIM 0. bullets: the one criterion (the title) is "subjective or vague" and excluded.
Assessment: wrong word. Nothing was verified; there was nothing to verify. A maintainer would read "verified" on a docs PR as noise at best and as a trust-eroding claim at worst. Needs a "not applicable / no behavioural change" state (F2). Same for #90, #95.

**3. CI-only: [#80](https://github.com/Mohith-c7/Radius/pull/80) ci(deps): bump checkout, setup-python, upload-artifact, pnpm/action-setup (5 workflow files).**
det: `verified` by R4 (0 criteria, 5 symbols, no tests, no findings). bullets: 1 criterion ("bump ... to current majors"), structural, unevidenced (no linked test), `insufficient_evidence` by R2b.
Assessment: the shipped output says `verified` on a supply-chain change that no test touches; the sensitivity output says the opposite for the same diff. Neither is sensible: the useful check here (are the new action versions pinned to full SHAs and do they match the upstream tag) is exactly what the repo's own `test_workflow_action_pins.py` does, and the pipeline cannot know that. Related #87 (docker hardening) is `failed` solely because a Trivy step has `continue-on-error: true`; it may be intended, which a reviewer can decide in ten seconds, so `failed` overclaims.

**4. PR with tests: [#84](https://github.com/Mohith-c7/Radius/pull/84) fix(ci): accept comma-separated scopes in the commit check (3 files: script, test, doc).**
det: R2a. bullets: 1 criterion (the title), behavioural, **unevidenced** although 12 tests are linked to the changed symbol; every item is `no_counted_evidence`, S 0.00; `insufficient_evidence` by R2b.
Assessment: this is the case the product exists for and it shows the weakest link: a small fix with a dedicated test is reported as unevidenced. The probable reason (criterion text "accept comma-separated scopes" shares few tokens with the symbol and test names, so criterion-to-symbol linking finds no edge and the 12 tests are gated; I did not instrument which link was missing, so this is unverified) is lexical linking meeting short, terse titles. A maintainer would say "there is a test for exactly this, why is it unevidenced?".

**5. PR without tests: [#3](https://github.com/Mohith-c7/Radius/pull/3) Codex/dashboard phase1 (27 files, 20 JS/TS).**
det and bullets: no criteria (title and body contain no bullets), `insufficient_evidence` by R2a plus `analysis_degraded` (`unsupported_language:typescript`); 37 symbols, 31 unlinked, 0 tests linked.
Assessment: the verdict is right in effect (a non-reviewable feature drop with no evidence) but for the wrong reason: the pipeline cannot read TypeScript symbols to link tests, so it would say the same about a perfectly tested TS PR. The "degraded" note is the honest part; it should be the headline, not a footnote.

**6. Tamper false positive: [#40](https://github.com/Mohith-c7/Radius/pull/40) fix: refresh uv.lock, make settings/tests independent of a local .env, drop unused trace carrier (11 files).**
det: 0 criteria, `failed` by R1c (T001 `test_deleted`, high, confidence 0.85; plus T017 low for the root `conftest.py` change). bullets: 7 criteria, 2 weak, 4 unevidenced, 1 excluded, still `failed`.
Assessment: the deleted test was renamed and reduced to match the removal of the `TRACE_CARRIERS` store the PR announced. The rule saw a deletion with surviving callee names. `failed` here is simply wrong and would be called out on the first PR where a maintainer looked. Proposed fix in F-T1 below.

**7. Tamper false positives that look like real signals: [#101](https://github.com/Mohith-c7/Radius/pull/101) feat(api,docs): OpenAPI 3.1 contract (23 files) and [#91](https://github.com/Mohith-c7/Radius/pull/91) feat(api): HTTP hardening (22 files).**
det: 9 and 4 tamper findings; the decider is a single T002 `runtime_skip` high (an environment-guard `pytest.skip(...)` inside a new test); the rest are 7 low `# noqa`/`type: ignore` notes, a medium `# pragma: no cover` and a medium retry marker. Both `failed` by R1c; bullets mode the same.
Assessment: nine findings on one PR is a wall of low-severity lint noise (T013 alone is 42 of 72 findings across the sample and 100% of them were `# noqa` / `type: ignore` in a repo that uses `ruff` with explicit rule codes). The real information, "this new test can skip itself", is correct but a guard on an optional dependency is a normal pattern. A maintainer would say: show the skip as a one-line note, don't fail the PR.

**8. Huge PR: [#100](https://github.com/Mohith-c7/Radius/pull/100) feat: Verdict v2 alpha (120 files, +30k lines, 1,355 symbols, 1,009 linked tests).**
det: `insufficient_evidence` by R2a (0 criteria), degraded: JS/TS unsupported and `truncated`; 103-145 s per run, peak 360 MB. In one sensitivity pass four producers timed out (criterion links, test links, assertions, relevance); tamper returned 82 findings in one run and none in another (F4).
Assessment: the pipeline survives but is at the edge of its own limits: Stage A alone took 95 s against a 120 s overall budget. The output for the largest and most consequential PR of the project is "no criteria, unlinked, degraded", which is honest and useless. Also a good demonstration that the 300-file skip cap is not what protects the system; time is.

**9. Failure / degraded: [#107](https://github.com/Mohith-c7/Radius/pull/107) feat(verdict-v2): policy engine and waivers read from the base branch (53 files).**
First run (before the fix): `StageAError: tamper_timeout` after 87 s (so v2 would have fallen back to v1). Fixed run: 62 s, 7 low findings, `insufficient_evidence` by R2a (det); sensitivity run: criterion-link producer timeout, `truncated`, coverage 0.0.
Assessment: timeouts of a *critical* producer turn into "no v2 verdict at all" for the PRs that are most worth looking at (large, many files). 5 of 29 PRs (#9, #28, #35, #103, #107) had that outcome before the `GitSnapshot` fix; none after. The degraded path works as designed (no crash, no false verdict), but it should say why in plain words.

**10. Non-Python / dependency: [#82](https://github.com/Mohith-c7/Radius/pull/82) fix(deps): patch Next.js and transitive JS advisories.**
det: `verified` by R4 (0 criteria). bullets: 5 criteria: two non-functional ("0 critical/high advisories", "Dependabot ..."), "needs typed evidence", unevidenced; `insufficient_evidence` by R2b.
Assessment: the sensitivity result is the more truthful one (the claim "0 critical/high" can only be backed by `pnpm audit` output, which the system does not ingest). The shipped `verified` is a false comfort. The non-functional typing ("needs typed evidence") is the one place where the output points at the right missing artefact.

**11. Test-only change: [#106](https://github.com/Mohith-c7/Radius/pull/106) test(analysis): loosen the tamper performance bound for shared CI runners (1 file).**
det: `verified` by R4 (0 criteria, 1 changed symbol, no findings, no behavioural symbols).
Assessment: ironically the most interesting case for a tamper system. The PR *relaxes a performance assertion* on a test; the tamper catalog has weakening rules (assertion loosened) but none fired. Possible reasons: the change is a numeric constant (T004 is conjunct-based), so a loosened numeric bound is not modelled. Not verified further. A maintainer would want exactly this PR flagged `needs_review`, and got `verified`. This is the gap between "tamper rules for removal/skip" and "tamper rules for relaxation".

**12. Golden fixtures with a flagged conftest: [#22](https://github.com/Mohith-c7/Radius/pull/22) test(bench): add 8 golden intent-to-evidence fixtures (98 files).**
det: `failed` by R1c: T017 `collection_hook` high (`collect_ignore` in `benchmarks/fixtures/intent/conftest.py`), plus a medium T012 "unverified dependency" for the deliberately hallucinated `pytimeparse-ultra` in a fixture and several T016 low `print` findings in fixture code. bullets: 3 criteria (two excluded, one unevidenced), still `failed`.
Assessment: the T012 finding on a fixture whose purpose is a fake dependency is a "true positive about content, false positive about meaning". The rules do not know that `benchmarks/fixtures/**` is intentionally broken code; the repo already has an allowlist for gitleaks (#94) for the same reason. Fixture and benchmark directories need an exclusion mechanism that is itself reviewed (the policy and waiver files from #107 are the natural place, but the replay does not exercise them).

Also read but not written up: #45 (licence, `verified` det, `insufficient` bullets), #50, #53, #86, #94, #95, #105 (17 tamper findings, almost all `# noqa` and `print`), #109 (T004), #110 (6 criteria, 3 excluded as "untestable external" because they mention secrets or production), all in the JSON.

Findings that need a decision or a larger change (proposed fixes, not applied):

| ID | Finding | Proposed fix |
|---|---|---|
| F-X1 (F1) | Deterministic extraction yields 0 criteria on ordinary PR bodies; "Acceptance (VS-02) - ..." headings do not match | (a) Decide what the product promises when no intent is extractable: surface it as the headline ("no intent found, add a .radius/intent.yml or an Acceptance criteria section"), never a verdict. (b) Measure recall on a labelled sample (IN-09/IN-10) before adding rules. (c) Candidate extractor extensions to evaluate, not to ship blind: prefix-tolerant section headings, "Summary"/"What changed" bullets and the title as low-weight proposals, always `proposed` and marked "inferred". Compare against the `bullets` mode here as a baseline, which gave 83 criteria of which 27 are excluded and none were proven. |
| F-X2 (F2) | R4 `verified` for PRs with no criteria and no behavioural symbols | Add a distinct outcome (for example `not_applicable` / "no behavioural change detected") or require at least one non-excluded criterion for `verified`; R2a should also fire when intent is missing and the PR changes security-relevant non-code files (workflows, Dockerfiles, lockfiles). Needs a design decision (verdict vocabulary is part of the contract). |
| F-T1 | T001 treats a renamed-and-edited test as deleted | In `DeletedTestRule`, treat an added test in the same file whose body (name stripped, `unparse`) is at least ~0.6 similar by `difflib` to the deleted one as renamed; keep the identical-text move rule. Add catalog cases for rename, rename plus edit, and delete plus unrelated add (must still fire). Attackers can still disguise deletions as renames; the similarity floor bounds that and should be tuned on data. |
| F-T2 | T002 `runtime_skip` is high and 0.8 confidence for any `pytest.skip()` in a body, including guards in new tests | Split: unconditional skip or skip nested under `if False`-like conditions stays high; a skip under an `if`/`try`/`importorskip`-style guard that references an import, platform, environment variable or file existence is `low`; a skip in a test that is new in the PR (no base counterpart) is capped at `medium`. |
| F-T3 | T013 (`# noqa`, `# type: ignore`) is 42 of 72 findings, all low, and appears on nearly every feature PR | Collapse into one finding per file with a count; do not list individually in the PR comment; exclude when the suppression carries an explicit rule code and already existed on the same logical line. Keep the data in the bundle. |
| F-T4 | Fixture and benchmark directories (deliberately broken code) trigger T012/T016/T017 | Path-based exclusions via the base-branch policy file; replay did not exercise policy/waivers, so this needs a run on a PR that carries them. |
| F-T5 | Tamper has no rule for relaxing numeric thresholds in assertions (#106) | New check under T004 for numeric constants in comparisons that move in the permissive direction in a test file; evaluate on `scripts/tamper_eval.py` mutants first. |
| F-P1 | Time budgets make the output depend on machine load (#100, #107); stage A of a 120-file PR is ~95 s against a 120 s overall budget | Budget by work units, not wall clock, or record the elapsed time and the budget in the bundle and mark the verdict `degraded` instead of silently dropping producers; raise the overall budget for `critical` steps; consider a persistent `git cat-file --batch` reader for the remaining reads. |
| F-L1 | Terse titles ("accept comma-separated scopes in the commit check") get no criterion-to-symbol link even when a dedicated test exists (#84) | Unverified cause (see case 4). Instrument which edge is missing in `Stage A` (log `criterion_symbol` and `criterion_test` edge counts), then measure; candidate: use changed-symbol names and docstrings as extra link keys. |
| F-L2 | TypeScript/JavaScript unsupported by Stage A | Known; replay shows how often it bites (4 of 29 PRs here, ~100% of the dashboard). Prioritise by how much of the target users' code is non-Python. |
| F-U1 | The explanation of "degraded" is a marker code (`unsupported_language:typescript`) | Render a plain sentence in the comment and the dashboard. |
| F-R1 | `agent_signal` fired on 28 of 29 PRs because of `Co-Authored-By` trailers, so independence discounts apply almost everywhere; it is not clear that is intended | Decide whether a co-author trailer alone should count as an agent signal. |

No crash of the pipeline was observed: 0 producer exceptions (`producer_failed:*`) in 58 runs; the only critical failures were the 5 timeouts (D1).

## 6. What this tells us about next steps

1. **Fix the front of the funnel before tuning the back.** The elaborate evidence machinery (assertion strength, relevance, noisy-or support) was exercised in sensitivity mode on 83 criteria and produced no `proven` criterion, 5 `weak`, 51 `unevidenced`. That is not evidence that the formulas are wrong; it is what you get when criteria are PR-summary sentences, links are lexical, and CI results are absent. Without real criteria (F1) and real CI per-case data, nothing downstream can be judged. The priority is intent recall on the PR text users actually write, measured on a labelled sample, and a convention (template, `.radius/intent.yml`) that makes intent explicit at near-zero cost to the author.
2. **A live F-06 run is more valuable than more replay.** With per-case CI results the as-shipped path stops being R2p and the whole static-versus-observed comparison becomes possible. The replay can be rerun against real uploads with the same script by replacing the all-green assumption.
3. **Non-Python code is most of this repository's PR volume** (workflows, Docker, Markdown, TypeScript, lockfiles). The system is silent there and says `verified` (F2). Decide the product stance (explicit "not covered") before extending language support.
4. **Tamper rules: precision matters more than coverage right now.** Three of seven `failed` verdicts were false or overstated and 42 of 72 findings were low-noise lint suppressions. The catalog has fixtures and a mutant evaluation (`scripts/tamper_eval.py`), but severities are "assumed" (D12) and there was no real-code false-positive measurement until this run. Replay more repositories with this script (it needs only a git checkout and `gh` read access) to estimate false-positive rates, then set severities and the `failed` threshold from data. Until then consider capping tamper at `needs_review` unless the finding is corroborated by a failing test.
5. **Runtime and cost are acceptable but not comfortable.** Median 20 s and p95 68 s per PR on a laptop with Windows process-spawn overhead, 148 MB median, no network, no LLM. The cliff is large PRs (60 to 125 s) and the fixed 120 s budget. Parallelising independent producers inside a PR and replacing per-file `git show` with a batch reader would remove most of it.
6. **Reproducibility hygiene.** The replay shows output varying with load (F4). Before any pre-registered use of the pipeline, deterministic budgets (work-unit based) are a prerequisite, as are fixed seeds and recorded algorithm versions (already in the bundle).
7. **Do not cite this document as validation.** It is a smoke test with commentary. A real evaluation needs other repositories, authors who did not build the tool, a gold set, and outcomes such as reverts and follow-up fixes (right-censoring per `DATA_HYGIENE.md` section 5).
