# Releasing and commit conventions

Status: **no release has been cut and there is no release automation yet.** Image publishing, signing and provenance are planned as PRD-13 in the [production-readiness backlog](production-readiness/BACKLOG.md). This page records the conventions that already apply and the manual steps a release would follow until then. Update it when PRD-13 lands.

## Commit and pull-request titles

History on `develop` is made of merge commits, so the **pull-request title** is what readers see. Both the title and every commit subject in a pull request must follow [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):

```text
type(scope)!: description
```

- Allowed types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`.
- `scope` is optional (`api`, `worker`, `intent`, `dashboard`, ...). `!` marks a breaking change.
- Header at most 100 characters; a space after the colon; lowercase type.
- Put the task id in the title or body, for example `feat(intent): add snapshot diff (IN-06)`.
- Not checked: `Merge ...` and `Revert "..."` commit subjects generated by git or GitHub, pull requests opened by bots (Dependabot and any `[bot]` account), and owner promotions `develop -> dev` and `dev -> main`.

## The check

`.github/workflows/commit-lint.yml` runs `scripts/ci/commit_lint.py` (standard library only; tests in `tests/test_commit_lint.py`) on every pull request. It also requires a changelog fragment for `feat`, `fix`, `perf` and breaking changes unless the pull request has the `no-changelog` label; see [changelog.d/README.md](../changelog.d/README.md). Run it locally:

```bash
python scripts/ci/commit_lint.py --title "fix(api): reject empty key" --base-sha origin/develop --head-sha HEAD
```

### Making it a required check (owner action)

The check is **not** required, so it cannot block merging until the owner decides. To require it, add the status check `Conventional Commits` (the job name) to the protected branches. Either edit `$requiredChecks` in `scripts/apply-github-branch-protection.ps1` and re-run it (and mirror the change in [github-branch-protection.md](github-branch-protection.md)), or in GitHub go to Settings, Branches, the branch rule, Require status checks, and add `Conventional Commits`. A check name appears in that search box only after it has run once on the repository.

## Changelog

[CHANGELOG.md](../CHANGELOG.md) follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). Contributors add fragments to `changelog.d/`; they do not edit `CHANGELOG.md` for ordinary changes.

## Cutting a release (manual, until PRD-13)

1. Confirm `develop` is green (`CI`, `Coverage`, `Security`) and promote `develop -> dev -> main` as described in the [development guide](DEVELOPMENT_GUIDE.md); only an owner promotes.
2. Choose the version under [Semantic Versioning](https://semver.org/). While the major version is 0, any change may break. Say which interfaces are public (HTTP API, GitHub Action inputs, CLI) in the release notes; no public API has been declared yet.
3. On a branch `chore/release-<version>`, fold the fragments in `changelog.d/` into a new `## [<version>] - <date>` section of `CHANGELOG.md` (Added, Changed, Deprecated, Removed, Fixed, Security), delete the folded fragments, leave an empty `## [Unreleased]`, update the comparison links, and set the version in `pyproject.toml` and the `package.json` files.
4. After that pull request merges, tag the merge commit on `main` (`git tag -a v<version>`; signing is not set up yet) and publish release notes from the changelog section.

Not yet available: container images, signed artifacts, SBOM attached to a release, provenance. Do not describe a release as signed or reproducible until they exist.
