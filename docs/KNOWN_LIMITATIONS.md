# Known limitations and open risks

Radius is an alpha. This page lists what is weak, missing or unproven, what reduces the risk
today, and where the fix is tracked. "Verified" means run by hand or by CI on 2026-11-03 (see the
status section of the [README](../README.md)); everything else is untested. Tracking ids point to
[production-readiness/BACKLOG.md](production-readiness/BACKLOG.md) (PRD-xx),
[research/tasks](research/tasks/) (task ids such as CA-xx, EV-xx, IN-xx) and
[research/ALIGNMENT_LOG.md](research/ALIGNMENT_LOG.md).

## 1. Verdict quality

| Limitation | Mitigation today | Planned fix / tracked in |
|---|---|---|
| **Static evidence only.** Verdict v2 rates tests by the shape of their assertions and by graph and name links. It does not check that a test would fail if the code were wrong. "Supported" is not "correct". | Wording says SUPPORTED, not proven; the alpha banner, `evidence_basis: static_only` and `calibrated: false` are in every v2 payload; the Check Run is advisory (`neutral`) by default (DEC-030). | Mutation-based evidence strength is wired behind `RADIUS_FEATURE_MUTATION` (default off, sandbox required, DEC-035): measured tests use a Wilson lower bound of their kill rate instead of the static cap. Bounded sample of one fault family, symbol-level links, synchronous in the analysis job; fixture sanity only ([MUTATION_WIRED.md](research/evaluation/MUTATION_WIRED.md)), RQ2 not run. |
| **Tamper severities are assumed.** Verdict v2 rule R1c turns one high-severity tamper finding into `failed`; the severities were never calibrated. In the first 2026-11 replay 3 of 7 such decisions looked wrong; re-run on current code ([REPLAY_2026-11-rerun](research/evaluation/REPLAY_2026-11-rerun.md)) 2 of 29 PRs are `failed` in the shipped mode and 3 of 29 in `summary` mode, at least two of them overstated or wrong on reading (a CI `continue-on-error`, a renamed-and-rewritten test), and the set changes from run to run because of time budgets. | The check conclusion is `neutral` by default (advisory); waivers and base-branch policy can silence a rule. A tamper-only `failed` should be read, not trusted. | Re-run findings F-T1b, F-T4, F-T5, F-T6 and F-P1 (load-dependent output) are open. |
| **Fixture agreement is not accuracy.** "7 of 8 fixtures match" (`docs/research/evaluation/FIXTURE_E2E.md`) compares the pipeline with expectations the same authors wrote and tuned the thresholds on; the gold harness also feeds the expected links in as hints on confirmed criteria. It shows the pipeline behaves as designed, not that it is right on real PRs. | None yet beyond this statement. | Held-out gold set (IN-09/10, calibration pack). |
| **Thresholds fitted to 8 fixtures.** `cap_static` 0.60 and `tau_support` 0.50 were chosen so the F-14 fixtures behave as designed. There is no held-out set, so no error rate (for example a false-verified rate) is known. | Parameters are versioned (`alpha-static` profile) and shown in each verdict; policy overrides have narrow ranges ([policy](policy.md)); the fixtures are regression tests only. | Held-out evaluation and calibration: CA-xx tasks, ALIGNMENT_LOG recommendation 4. See [verdict-v2.md](verdict-v2.md). |
| **Extraction recall is low by default.** The default `sections` mode reads only acceptance-style sections, checklists, Gherkin and spec files, so typical PR descriptions yield no criteria and the result is `insufficient_evidence` (measured on this repository's 29 PRs in the [re-run](research/evaluation/REPLAY_2026-11-rerun.md): 29 of 29 had no criteria in `sections`; `summary` found at least one on 11, none proven). | `RADIUS_INTENT_EXTRACTION_MODE=summary` (opt-in) proposes low-weight, never-confirmed criteria that block `verified` until confirmed (DEC-032); humans can add and confirm criteria in the dashboard; zero criteria never gives `verified` (DEC-031). | IN-09/IN-10 (gold set; real precision/recall numbers pending); IN-12 author prompts, not built. |
| **Author-controlled evidence.** The PR author writes the description, the criteria and the tests, and can add link hints. A motivated author can steer the verdict. | Hint edges that do not come from the base branch or a human confirmation are capped (DEC-030); tamper rules flag weakened or deleted tests; evidence is bound to the head SHA; `.radius/` policy and waivers are read from the base branch, with expiry. See the [threat model](security/VERDICT_V2_THREAT_MODEL.md). | Process verification and agent-authorship signals: PR-xx tasks; external review: PRD-30. Residual risk stays open. |
| **Linking quality unmeasured on real code.** Criterion-to-symbol and symbol-to-test linkers were evaluated on synthetic fixtures only; the 0-100 v1 score is an uncalibrated heuristic. | Reason codes and chain confidence are shown; weak links route to review. | LK-07 (link gold set), CA-xx. |
| **Unanalysable changes block `verified`, they are not analysed.** Files in other languages, Dockerfiles, SQL, generated or vendored paths and test files the tamper engine cannot read give `unsupported_language:*`, `unanalyzed_files:<n>` or `tamper_unanalyzed:*` (DEC-037). Dependency manifests and CI/build configuration are only checked by the tamper catalog; lockfiles count as inert. | The markers are blocking and listed in the comment, the payload and the dashboard. | Deeper manifest and config analysis: not scheduled. |
| **Who confirmed a criterion is only as strong as the sign-in behind it.** The confirmer is the authenticated principal (a signed-in dashboard user, else the API key), never a header (B-07, DEC-040). A user signed in with GitHub is compared with the PR author's login: the author never lifts their own cap. A confirmer whose GitHub link is unknown (password user, API key) still counts by default but is shown as `unverified confirmer`; an author holding the organisation's API key can still confirm as the key. | `RADIUS_VERDICT_V2_CONFIRM_POLICY=require_second_person` counts only a confirmer verifiably linked to a different GitHub account; see the [threat model](security/VERDICT_V2_THREAT_MODEL.md). | Per-person API credentials; PR author GitHub id (the check compares logins, which can be renamed). |
| **Re-scoring needs the stored Stage A.** A bundle whose Stage A exceeds 8 MB loses it (`stage_a_dropped`); CI results then cannot re-score it and the verdict becomes "unavailable" (`stage_a_not_stored`) instead of staying on the old text (B-04). The changed outbox claim handling (B-16) and the sweep (B-09) were tested on SQLite and in memory only, not on Postgres. | Visible error revision, `action_required` conclusion. | Store Stage A in its own column. |
| **Python-first.** Verdict v2, tamper rules and symbol-level impact are Python only. TypeScript/JavaScript has dependency edges; Go, Java and Rust have symbols only. | Unsupported cases fall back to the full suite or `insufficient_evidence`. | Not scheduled. |
| **Test selection measured on a small corpus.** | Falls back to the full suite when the graph cannot map a change. | [benchmark](benchmarks/REAL_REPO_BENCHMARK.md); PRD-23. |

## 2. Platform and operations

| Limitation | Mitigation today | Planned fix / tracked in |
|---|---|---|
| **Live GitHub is untested.** Webhook delivery, GitHub App installation, installation tokens, rate limits, check runs and PR comments were exercised only against an in-memory fake (smoke test in CI). No public URL was available and tunnels are not allowed. | Webhook signature, replay and permission paths are covered by tests; a validation runbook exists. | F-06; [GitHub App validation runbook](github-app-validation/RUNBOOK.md); needs a deployed URL (owner). |
| **Production mode not run.** `docker compose up` without the dev override (https origins, real SMTP, managed API keys) was not run; the docs for it are derived from code and marked Unverified. | Compose files are checked statically (`scripts/check_compose.py`); production validation rejects unsafe settings. | PRD-25, PRD-17. See [INSTALL](operations/INSTALL.md). |
| **Dev-mode behaviours.** `make dev` auto-verifies accounts, prints sign-in links in logs, has one random dev API key, allows localhost CORS, and can load a demo login with a public password. | The dev override is a separate file; seeding refuses `RADIUS_ENV=production`; docs say never to expose it. | By design. |
| **SSO is new and lightly verified.** Password sign-in (with e-mail verification) and Google/GitHub OAuth/OIDC sign-in exist ([SSO design](security/SSO_DESIGN.md)); the OAuth flows were exercised against fakes only, there is no SAML, SCIM or per-organization RBAC beyond the `admin`/`developer` role, and the dashboard is **single-tenant** (every signed-in user sees the one organization configured in `RADIUS_ORGANIZATION_ID`; see [HTTP_HARDENING](security/HTTP_HARDENING.md)). | Sessions and API keys are hashed and scoped; the dashboard validates the session against the API on every request; see [HARDENING](operations/HARDENING.md). | PRD-26. |
| **No release has been published or signed.** `release.yml` can build, scan, generate SBOMs and, only when the repository variable `RADIUS_RELEASE_PUBLISH` is `true` and the `release` environment is approved, push and cosign-sign images; it has never run on GitHub. By default nothing is pushed. Images are otherwise built from the checkout. | CI scans (CodeQL, dependency audit, image scan, gitleaks, Scorecard 7.4) run on develop. | PRD-13, PRD-14, PRD-32. See [RELEASING](RELEASING.md). |
| **No external penetration test; DAST is a baseline only.** `.github/workflows/dast.yml` runs an OWASP ZAP baseline (passive) scan against the API and dashboard; there is no authenticated active scan. | SAST, dependency, secret and container scans in CI ([CI checks](security/CI_CHECKS.md)); HTTP hardening and tenant-isolation tests. | PRD-27, PRD-30, QS-03. |
| **Sandboxed test execution is experimental.** Off by default and fails closed; no penetration test; Windows sandbox tests not run. | [Isolation notes](security/EXECUTION_ISOLATION.md). | QS-03, F-07. |
| **Dashboard browser coverage is thin and there is no accessibility CI.** A headless-browser e2e (sign-up, main pages, sign out/in) runs in CI; the verdict panel, the confirm button and the new connect/analyze buttons were exercised by hand in Chrome or by node tests only, and the intent upload and JUnit upload buttons were never clicked (CI runs build checks on every PR). | A manual Chrome run of the main flows (README status). | PRD-22. |
| **Single maintainer, capstone origin.** Bus factor of one; a second author's commits and the capstone sponsor relationship are unresolved for licensing. | Apache-2.0 files are in the repository; DCO sign-off. | PRD-01 (owner); see [RELEASE_CHECKLIST](RELEASE_CHECKLIST.md). |
| **Backup/restore, upgrade/downgrade and several worker replicas** are documented from code, not run. | Marked Unverified in the [operations docs](operations/README.md). | QS-11, PRD-28. |

### Security review A follow-ups (2026-11)

These remain after the fixes in [CODE_REVIEW_A_RESPONSE](security/CODE_REVIEW_A_RESPONSE.md).

| Limitation | Mitigation today | Planned fix / tracked in |
|---|---|---|
| **No customer-facing proof that a tenant controls a GitHub installation.** Multi-tenant deployments must link `organizations.github_installation_id` by an operator step (or use explicit single-tenant mode); `connect-github` and webhooks no longer attach an installation on the strength of a repository name. | Rule and rationale in [INSTALLATION_BINDING](security/INSTALLATION_BINDING.md); refused with `403 GITHUB_INSTALLATION_NOT_LINKED`. | Authenticated install/OAuth callback flow: OWNER decision (needs UI and an OAuth permission decision). |
| **Repository ownership on `POST /repositories` is caller-asserted.** The first organization to register a numeric GitHub repository id owns that row; others get 409. Webhook routing no longer trusts that row alone (an installation linked to another organization wins and is refused for the row's owner, and an unlinked installation is not routed to it outside single-tenant modes). | Clone URLs are validated (https, allow-listed host, `owner/repo`), the token only goes to allow-listed hosts, and caches are per organization. | Verify ids against GitHub with the linked installation (same OWNER decision as above). |
| **In uat/production the verify-email page sets the password.** The password chosen at signup is discarded at verification (pre-hijacking defence); the mailbox owner chooses one on the verify page, in the same step (A-07, DEC-040). A link that is not used with a password leaves the account without one until "Forgot password" or OAuth. | Development and test behave as before (no password asked). | None. |
| **Signup is indistinguishable for new and registered addresses only in uat/production.** There the response is the same 201 and the owner of a registered address is told by e-mail; development keeps the clear 409. The response time is the same class (one password hash, mail sent in the background) but not constant-time. | A-12, DEC-040. | None. |
| **Login throttle is in memory, per process.** 10 failures per account per 15 minutes then 429 (also for the right password, so a known email can be locked out for 15 minutes); the per-IP limit is unchanged. Multi-replica deployments get N times the budget. No shared store exists for it: the PostgreSQL tables (`idempotency_keys`, `analysis_jobs`) are not rate-limit stores and a new table was not added (DEC-040). | Argon2 work is constant for unknown accounts. Run one API replica, or rate-limit `/api/v1/auth/*` per IP and per account at the reverse proxy / WAF (documented in HARDENING). | Shared rate-limit store behind the existing seam in `middleware/rate_limit.py`. |
| **The analysis pipeline still runs in one database transaction.** The runner works in bounded units: no connection is held open during GitHub calls, git clone / fetch / checkout, intent ingestion or result publication (C-04, DEC-040). The pipeline itself (diff, parse, graph, test selection and execution, scoring) is one transaction on purpose: committing it in stages would leave partial artefacts (and repository-level test history) after a crash. | A connection is held while the sandbox runs the tests; size the pool for the number of worker slots. | Pipeline split into compute-then-write once every store has a replay-safe write path.
| **Test outcomes are produced by PR-controlled code.** A `conftest.py` or test can emit any JUnit file or exit code; CI uploads are bound only to the commit sha. The sandbox contains the code, not the evidence. | Verdict wording ("supported", not "proven"), tamper rules, base-branch policy. | By design; see the verdict v2 threat model. |
| **Sandbox results directory is `0777` inside a `0700` per-run scratch root.** The container user (nobody) must be able to write the report. Only a host root user can reach it. | Scratch root created `0700`; artifacts are read only as regular non-symlink files. | A user-namespace mapped directory when rootless Docker is the supported mode. |
| **Webhook replay.** Signed payloads carry no timestamp; GitHub redeliveries are deduplicated by delivery id, a replay with a fresh id is accepted. Concurrent redeliveries can both process. | Idempotency per delivery id and body hash. | Inherent to GitHub's scheme. |

## 3. Research

| Limitation | Mitigation today | Planned fix / tracked in |
|---|---|---|
| **Not pre-registered or frozen.** The pre-registration is a draft with no freeze commit, tag or archive deposit. Any result so far is exploratory. | The docs describe hypotheses, not results; the 2026-11 replay is labelled exploratory ([REPLAY](research/evaluation/REPLAY_2026-11.md)). | EP tasks; [PREREGISTRATION](research/preregistration/PREREGISTRATION.md); owner decision on deposit (PRD-31). |
| **Gold set has a single annotator.** The plan calls for two independent annotators with adjudication and at least 150 PRs; agreement cannot be measured with one. | Tooling and guidelines exist ([annotation](research/annotation/RUNBOOK.md)); no quality claim is made from the set. | IN-09, LK-07, EP-04. |
| **Calibration not done.** No reliability curve, and no abstention threshold justified by data. | Everything is labelled `heuristic_uncalibrated`. A tested measurement and guard toolkit exists but is not wired in and has seen no real labels ([CALIBRATION_TOOLKIT](research/evaluation/CALIBRATION_TOOLKIT.md)); it also records an open question about the loss in the pre-registration's conformal procedure. | CA-xx. |
| **Novelty not systematically reviewed.** | The README claims only what the [novelty assessment](research/literature/novelty-assessment.md) supports. | EP literature tasks. |
